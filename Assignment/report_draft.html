1. Introduction

Multithreading allows a program to do more than one task at the same time inside a single process. Every programming language gives its own library or API to create and manage threads, but under the surface they all depend on the operating system in different ways. In this report, I have compared three threading systems: the Python threading module, POSIX pthreads (used mainly in C/C++), and the threading options available in Swift. For each one, I have discussed the library implementation, how it works with the operating system, and how the user-level threads are mapped to kernel-level threads. At the end, I have compared their efficiency and overhead in different situations.

2. Python Threads

2.1 Library Implementation

Python provides threading through two modules. The low-level module is called _thread, and on top of it there is the high-level threading module, which is the one programmers normally use. The threading module gives a Thread class to create and start threads, and it also gives synchronization tools like Lock, RLock, Semaphore, Event, Condition, and Barrier (Python Software Foundation, 2026). Making a thread is very simple: we just pass a function to the Thread object and call start().

Python threads are preemptive, not cooperative. A thread does not need to give up control by itself; the operating system can pause it at any time. However, the standard CPython interpreter has a special rule called the Global Interpreter Lock (GIL). The GIL allows only one thread to run Python bytecode at a time, even if the computer has many CPU cores. The interpreter forces a running thread to release the GIL after a small time interval (by default 5 ms), so other threads get a chance to run (Python Software Foundation, 2026). So the switching is still preemptive, but true parallel execution of Python code is blocked by the GIL. It should be noted that recent Python versions (3.13 and later) added an optional "free-threaded" build where the GIL can be disabled, but the normal build still keeps the GIL.

2.2 OS Integration

Python does not implement its own scheduler. Every Python thread is actually a real thread of the operating system. On Linux and macOS, CPython creates the threads using the POSIX pthread API, and on Windows it uses the native Windows thread API. Because of this, the threading module is cross-platform: the same Python code runs on Windows, Linux, and macOS without any change, and Python hides the platform differences from the programmer.

Since Python threads are real OS threads, they get all the normal performance optimizations that the OS gives, such as scheduling across multiple cores, thread priorities, and fast synchronization primitives (for example, futex on Linux). But the GIL cancels most of the multi-core benefit for CPU-bound Python code. That is why Python threads are mainly useful for I/O-bound work (network requests, file reading, waiting), because the GIL is released during blocking I/O calls, so other threads can continue running (Python Software Foundation, 2026).

2.3 Mapping Between User-Level and Kernel-Level Threads

Python uses a one-to-one (1:1) mapping. Each Python thread is directly mapped to one kernel-level thread, and the OS kernel schedules all of them (Silberschatz et al., 2018). Python does not do any scheduling of its own; the only extra control is the GIL, which decides which thread can run Python bytecode at a moment. So the model can be described as kernel-level threads with an interpreter-level lock on top. The overhead of creating a Python thread is the same as creating an OS thread, plus some interpreter bookkeeping. For CPU-bound parallel work, Python programmers usually use the multiprocessing module instead, because separate processes do not share one GIL.

3. POSIX Pthreads

3.1 Library Implementation

Pthreads (POSIX threads) is not a product of one company; it is a standard API defined by IEEE in the POSIX standard (IEEE 1003.1c). It is a C library, and the header file is pthread.h. The standard defines around 100 functions, and the main ones are pthread_create(), pthread_join(), pthread_exit(), and pthread_detach() for thread management. For synchronization it gives mutexes (pthread_mutex_t), condition variables (pthread_cond_t), read–write locks, and barriers (Butenhof, 1997). Pthreads gives the programmer very fine control, for example setting stack size, scheduling policy, and thread priority through attributes.

Pthreads is preemptive on all common systems. The kernel scheduler can stop any thread when its time slice finishes and give the CPU to another thread. A pthread does not need to yield voluntarily, although a function sched_yield() exists if a thread wants to give up the CPU early.

3.2 OS Integration

Pthreads is the closest of the three to the operating system, because it is basically a thin wrapper over kernel system calls. On Linux, the implementation is called NPTL (Native POSIX Thread Library), which is part of glibc, and it creates threads with the clone() system call. On macOS and BSD systems, pthreads is implemented on top of the native kernel threads of those systems. Pthreads is a standard, so it is cross-platform among POSIX systems (Linux, macOS, BSD, Solaris, etc.), but Windows does not support it natively; on Windows we need a compatibility layer like pthreads-win32 or we must use Windows threads directly (Barney, 2023). So it is portable, but only inside the Unix family.

The OS gives many optimizations for pthreads. On Linux, mutexes are built on futexes (fast user-space locks), so if there is no contention, locking does not even enter the kernel. NPTL was specially designed so that creating and destroying many threads is fast, and the kernel scheduler is O(1)/CFS based, so it can handle thousands of threads. The kernel also tries to keep a thread on the same CPU core (processor affinity) to use the cache better.

3.3 Mapping Between User-Level and Kernel-Level Threads

Modern pthreads implementations use the one-to-one model: every pthread is one kernel thread, and the kernel scheduler manages all of them directly (Silberschatz et al., 2018). In the past, some systems (like old Solaris) used a many-to-many model for pthreads, but that has been abandoned because the 1:1 model is simpler and modern kernels are fast enough. The advantage of this mapping is real parallelism: if the machine has 8 cores, 8 pthreads can really run at the same time. The disadvantage is that every thread creation, context switch, and blocking operation involves the kernel, which is heavier than pure user-level threads. Still, for CPU-bound work, pthreads normally gives the best performance among the three systems in this report because there is no interpreter and no lock like the GIL.

4. Swift Threads

4.1 Library Implementation

Swift actually has three layers of threading tools. First, there is the Thread class from the Foundation framework, which is a direct object-oriented wrapper around one OS thread, similar to pthreads but easier to use (Apple Inc., n.d.-b). Second, and much more commonly used, is Grand Central Dispatch (GCD, also called libdispatch). In GCD, the programmer does not create threads manually. Instead, we submit small tasks (closures) to dispatch queues, and the system manages a pool of worker threads automatically (Apple Inc., n.d.-a). Third, modern Swift (5.5 and later) has structured concurrency with async/await, actors, and tasks, which runs on a cooperative thread pool.

About preemptive versus cooperative: the underlying OS threads are always preemptive, because the kernel can interrupt any thread. Thread and GCD tasks are therefore preemptively scheduled. But the modern Swift Concurrency model is interesting because it is cooperative at the language level: the runtime keeps only about one thread per CPU core, and an async task gives up its thread only at await suspension points. So Swift mixes both styles: cooperative task switching on top of preemptive kernel threads.

4.2 OS Integration

On Apple platforms (macOS, iOS), Swift threading sits on top of Mach kernel threads and the pthread layer of Darwin. GCD is deeply integrated with the OS: the kernel itself helps libdispatch decide how many worker threads should exist depending on the system load, and it supports Quality of Service (QoS) classes, so background work can run with low priority and save battery (Apple Inc., n.d.-a). This tight integration is a big optimization, because the thread pool does not create too many threads (avoiding "thread explosion") and the scheduler understands the priority of each queue.

Swift itself is cross-platform now (it runs on Linux and Windows, where libdispatch has been ported), but honestly the best support and optimization is still on Apple platforms, so in practice Swift threading is more platform-dependent than Python or pthreads. Foundation's Thread on Linux is implemented over pthreads.

4.3 Mapping Between User-Level and Kernel-Level Threads

The mapping depends on which layer we use. The Foundation Thread class is a pure one-to-one mapping: one object equals one kernel thread. GCD is closer to a many-to-many (hybrid) style: many submitted tasks are multiplexed over a small pool of kernel worker threads, and the OS controls the pool size. Swift Concurrency is also a hybrid/cooperative model: a large number of lightweight tasks are scheduled by the Swift runtime onto a fixed pool of kernel threads (about one per core), and switching between tasks happens in user space at await points, which is much cheaper than a kernel context switch (Apple Inc., n.d.-a; Silberschatz et al., 2018). This gives Swift very low overhead for a huge number of concurrent tasks, which is very useful for server and UI applications.

From the efficiency point of view, the three libraries are good at different things. For CPU-bound work (heavy calculation), pthreads is the winner because the threads run native code in parallel on all cores with no interpreter overhead. Python is the weakest here because of the GIL: even with 8 threads, only one runs Python code at a time, so CPU-bound Python threading can even become slower than a single thread because of lock switching. Swift is close to pthreads for CPU work since it compiles to native code.

For I/O-bound work (many network or disk operations), all three are usable. Python threads work fine here because the GIL is released while waiting. But when the number of concurrent operations becomes very large (thousands), models that create one kernel thread per operation (raw pthreads, Python threads, Foundation Thread) become costly, because every kernel thread needs its own stack (often megabytes) and every switch needs a kernel context switch. In this scenario, GCD and Swift Concurrency are much more efficient, since thousands of light tasks share a few kernel threads and switch in user space (Apple Inc., n.d.-a).

In terms of programming effort and safety, pthreads gives the most control but is also the easiest to misuse (manual joins, manual mutex handling, data races). Python is the easiest to write but the least powerful. Swift sits in the middle: GCD and async/await hide the thread management and the actor model helps to avoid data races at compile time.

6. Conclusion

In summary, all three threading systems finally depend on kernel-level threads, but they expose them very differently. Pthreads is a thin, preemptive, 1:1 standard API that gives maximum control and true parallelism on POSIX systems. Python's threading module wraps the same kind of kernel threads in a very easy cross-platform API, but the GIL limits it to concurrency (mostly I/O) instead of real parallelism. Swift offers a range: a 1:1 Thread class, the OS-integrated GCD thread pool, and a modern cooperative task system that gives hybrid user/kernel scheduling with very low overhead. So the "best" library depends on the scenario: pthreads for raw CPU performance and control, Python for simple I/O-bound scripting, and Swift's GCD/Concurrency for applications with a large number of concurrent tasks.
